# เขียนเอกสาร SRS

แปลง `CONTEXT.md` (ภาษากลางของโดเมน) และ `docs/adr/*.md` (ข้อตัดสินใจ + ข้อจำกัด) ให้เป็นเอกสารข้อกำหนดความต้องการภาษาไทย 7 บท ที่ทุกข้อกำหนด **atomic, testable, traceable**

- **atomic** — หนึ่งรหัส = หนึ่งความสามารถที่ตรวจรับได้ ถ้าประโยคมี "และ/หรือ" ที่ตรวจรับแยกกันได้ ให้แตกเป็นสองรหัส
- **testable** — เขียนเป็นเงื่อนไขที่ผู้ตรวจรับชี้ผ่าน/ไม่ผ่านได้ ใส่ตัวเลขทุกครั้งที่วัดได้ ("ภายใน 2 วินาที" แทน "รวดเร็ว")
- **traceable** — มีรหัส และปรากฏในบทที่ 7 (RTM) ครบทุกรหัส

## กฎที่ใช้ตลอดทั้งเอกสาร

- **ภาษาไทย** เป็นภาษาหลัก ศัพท์เทคนิคคงคำอังกฤษไว้ได้ (API, endpoint, concurrent)
- **ศัพท์โดเมนใช้คำตาม `CONTEXT.md` เท่านั้น** — คำในบรรทัด `_Avoid_` ของแต่ละคำห้ามปรากฏในเอกสาร (เช่น ใช้ "Booking" ไม่ใช้ "Reservation")
- **diagram ทุกภาพเป็น mermaid** ในบล็อก ` ```mermaid ` พร้อมคำบรรยายใต้ภาพหนึ่งย่อหน้า
- **ข้อมูลที่ยังไม่รู้** ให้ลงเป็นแถวใน "ตารางสมมติฐาน" (บทที่ 2) และแท็ก `[ต้องยืนยัน]` ตรงจุดที่ใช้ — อย่าเดาแล้วเขียนเป็นข้อเท็จจริง
- **ข้อจำกัดทุกข้อต้องอ้าง ADR** ที่เป็นที่มา เช่น `(ที่มา: ADR-0002)`

## รหัสข้อกำหนด

จัดสรรรหัสก่อนเขียนร้อยแก้ว เพราะบทที่ 7 อ้างรหัสเหล่านี้ทั้งหมด

| ชนิด | รูปแบบ | ตัวอย่าง |
|---|---|---|
| ความต้องการเชิงหน้าที่ | `FR-<MODULE>-<nn>` | `FR-BKG-01` |
| ไม่ใช่เชิงหน้าที่ | `NFR-<หมวด>-<nn>` | `NFR-PERF-01`, `NFR-SEC-02` |
| ด้านข้อมูล | `DR-<nn>` | `DR-03` |
| ด้าน Interface | `IR-<nn>` | `IR-05` |
| Use Case | `UC-<nn>` | `UC-02` |
| ข้อ TOR | `TOR-<nn>` | `TOR-04` |

`<MODULE>` มาจาก aggregate ใน `CONTEXT.md` (เช่น `ROOM`, `BKG`, `EMP`) ไม่ใช่จากโครงสร้างโค้ด

## ขั้นตอน

### 1. ตรึงฐานอ้างอิง

อ่านให้ครบ: `CONTEXT.md` ทุกคำ, `docs/adr/*.md` ทุกไฟล์, และแหล่ง TOR ถ้ามี (มองหาใน `docs/requirement/`, `docs/tor/`)
ถ้ามีโค้ดในโปรเจกต์แล้ว ใช้ `get_architecture` และ `search_graph` ตรวจว่าโมดูลที่จะเขียนตรงกับของจริง

**เสร็จเมื่อ** ทุกคำใน `CONTEXT.md` มีร่างแถวอภิธานศัพท์แล้ว และทุก ADR ถูกจับคู่กับบทที่มันไปบังคับ (ADR ที่ยังไม่มีบทรองรับ = ยังอ่านไม่ครบ)

ถ้าไม่พบ TOR ให้ประกาศตรง ๆ กับผู้ใช้ว่าคอลัมน์ TOR ในบทที่ 7 จะสร้างจากขอบเขตในบทที่ 1 และติดแท็ก `[ต้องยืนยัน]` แล้วเขียนต่อ

### 2. จัดสรรรหัสและโมดูล

ทำตารางจัดสรรรหัสทั้งชุด (FR / NFR / DR / IR / UC / TOR) ในสมุดร่างก่อน แล้วค่อยเขียนไฟล์
**เสร็จเมื่อ** ทุกโมดูลมีช่วงรหัส FR ของตัวเอง และทุกคำใน `CONTEXT.md` ที่มีสถานะ (state) ถูกทำเครื่องหมายว่าต้องมี State Diagram ในบทที่ 3

### 3. เขียนบทที่ 1 ถึง 6 ทีละไฟล์

ก่อนเขียนแต่ละบท เปิด [`references/sections.md`](references/sections.md) เฉพาะหัวข้อของบทนั้น และเปิด [`references/mermaid.md`](references/mermaid.md) เฉพาะชนิด diagram ที่บทนั้นต้องใช้
**เสร็จแต่ละบทเมื่อ** หัวข้อย่อยครบตาม `sections.md`, ตารางมีคอลัมน์ครบ, diagram ที่ระบุในแผนที่เอกสารมีครบทุกภาพ และทุกภาพมีคำบรรยายใต้ภาพ

### 4. เขียนบทที่ 7 (RTM) เป็นบทสุดท้าย

ไล่รหัสจากบทที่ 3–6 ทีละรหัสลงตาราง
**เสร็จเมื่อ** ทุกรหัส FR / NFR / DR / IR ที่นิยามไว้ในบทที่ 3–6 ปรากฏใน RTM อย่างน้อยหนึ่งแถว และทุกรหัสที่ RTM อ้างถึงมีนิยามจริงในบทของมัน — สองทิศทางนี้ต้องปิดครบ

### 5. ตรวจก่อนส่ง

ไล่ทั้ง 5 ข้อ:

1. **ศัพท์** — คำในบรรทัด `_Avoid_` ของ `CONTEXT.md` ไม่ปรากฏในไฟล์ใดเลย (ค้นทีละคำ)
2. **รหัส** — RTM ปิดครบสองทิศทางตามข้อ 4 และไม่มีรหัสซ้ำ
3. **mermaid** — รัน `node .claude/skills/srs/scripts/check-mermaid.mjs docs/sds` จนผ่านทุกบล็อก แล้วไล่รายการดักพลาดท้าย [`references/mermaid.md`](references/mermaid.md) ซ้ำอีกรอบสำหรับข้อที่สคริปต์จับไม่ได้
4. **testable** — ทุกแถว NFR มีตัวเลขและวิธีทดสอบ ไม่มีคำว่า "เหมาะสม" "รวดเร็ว" "ใช้งานง่าย" ลอย ๆ
5. **สารบัญ** — `README.md` ลิงก์ครบทั้ง 7 ไฟล์

แล้วรายงานผู้ใช้ว่าเขียนไฟล์อะไรบ้าง และมีแท็ก `[ต้องยืนยัน]` เหลืออยู่กี่จุด ที่ไหน

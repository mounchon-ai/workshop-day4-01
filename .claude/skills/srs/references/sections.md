# โครงเนื้อหารายบท

หัวข้อย่อยและคอลัมน์ตารางของทั้ง 7 บท เปิดเฉพาะหัวข้อของบทที่กำลังเขียน

---

## README.md (หน้าปก + สารบัญ)

- ชื่อระบบ, เวอร์ชันเอกสาร, วันที่, ผู้จัดทำ
- ขอบเขตของเอกสารชุดนี้หนึ่งย่อหน้า
- สารบัญลิงก์ไปทั้ง 7 ไฟล์ พร้อมสรุปหนึ่งบรรทัดต่อบท
- **ประวัติการแก้ไข** — `เวอร์ชัน | วันที่ | ผู้แก้ไข | รายการเปลี่ยนแปลง`

---

## บทที่ 1 — บทนำ (`01-introduction.md`)

**1.1 วัตถุประสงค์ของเอกสาร** — เอกสารนี้ใช้ทำอะไร ใครเป็นผู้อ่าน (ผู้ว่าจ้าง / ทีมพัฒนา / ผู้ตรวจรับ)

**1.2 ขอบเขตของระบบ** — ระบบทำอะไร แบ่งเป็นสองรายการชัดเจน:
- อยู่ในขอบเขต (In Scope)
- อยู่นอกขอบเขต (Out of Scope) — ดึงจาก ADR ที่ปฏิเสธทางเลือกไว้ พร้อมอ้าง ADR

**1.3 นิยามศัพท์และอภิธานศัพท์** — ตารางที่ถอดมาจาก `CONTEXT.md` ครบทุกคำ

| คำศัพท์ | ความหมาย | คำที่ไม่ใช้ | หมายเหตุ |
|---|---|---|---|

คอลัมน์ "คำที่ไม่ใช้" มาจากบรรทัด `_Avoid_` ตรง ๆ — ตารางนี้คือสัญญาว่าเอกสารทั้งชุดจะใช้คำอะไร

**1.4 เอกสารอ้างอิง** — ตาราง `รหัส | ชื่อเอกสาร | เวอร์ชัน | ที่มา` รวม `CONTEXT.md`, ADR ทุกฉบับ, TOR, มาตรฐานที่อ้าง (เช่น พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล)

## บทที่ 2 — ภาพรวมระบบ (`02-system-overview.md`)

**2.1 มุมมองผลิตภัณฑ์** — ระบบวางตัวอยู่ตรงไหนขององค์กร ต่อกับอะไรบ้าง
→ **System Context Diagram (DFD Level 0)**: ระบบเป็นวงกลมเดียวตรงกลาง ล้อมด้วย external entity และลูกศรที่ระบุชื่อ data flow ทุกเส้น

**2.2 ผู้ใช้งานและผู้มีส่วนได้ส่วนเสีย**

| กลุ่มผู้มีส่วนได้ส่วนเสีย | บทบาทต่อระบบ | ความคาดหวังหลัก | ระดับอิทธิพล | ความถี่การใช้งาน |
|---|---|---|---|---|

→ **Stakeholder Map** (mindmap)

**2.3 กระบวนการทำงาน**
→ **BPMN As-Is** — กระบวนการปัจจุบันก่อนมีระบบ ชี้จุดเจ็บปวด (pain point) ด้วยหมายเหตุใต้ภาพ
→ **BPMN To-Be** — กระบวนการหลังมีระบบ ระบุชัดว่าขั้นตอนไหนถูกแทนที่ด้วยระบบ
ทั้งสองภาพต้องใช้ lane เดียวกันเพื่อให้เทียบกันได้ และต้องมีย่อหน้าสรุปว่าอะไรเปลี่ยนไป

**2.4 ข้อจำกัด (Constraints)**

| รหัส | ข้อจำกัด | ประเภท (เทคนิค/ธุรกิจ/กฎหมาย) | ที่มา |
|---|---|---|---|

ทุกแถวอ้าง ADR หรือ TOR เป็นที่มา

**2.5 สมมติฐาน (Assumptions)**

| รหัส | สมมติฐาน | ผลกระทบถ้าสมมติฐานไม่จริง | สถานะ |
|---|---|---|---|

ทุกจุดที่ติดแท็ก `[ต้องยืนยัน]` ในเอกสารต้องมีแถวที่นี่

## บทที่ 3 — ความต้องการเชิงหน้าที่ (`03-functional-requirements.md`)

จัดกลุ่มตามโมดูล หนึ่งโมดูลหนึ่งหัวข้อย่อย (3.1, 3.2, …)

**เปิดหัวข้อด้วย Use Case Diagram รวมทั้งระบบ** แล้วจึงลงรายละเอียดทีละโมดูล

ในแต่ละโมดูล:

**ก. ตารางความต้องการ**

| รหัส | ชื่อฟังก์ชัน | รายละเอียด | ความสำคัญ (บังคับ/ควรมี/ถ้ามีเวลา) | Use Case ที่เกี่ยวข้อง |
|---|---|---|---|---|

เขียนรายละเอียดเป็นประโยค "ระบบต้อง…" หนึ่งประโยคต่อหนึ่งรหัส

**ข. Use Case Description** — ทำครบทุก UC ในโมดูล

| หัวข้อ | เนื้อหา |
|---|---|
| รหัส / ชื่อ | |
| ผู้กระทำ (Actors) | |
| คำอธิบายย่อ | |
| เงื่อนไขก่อนเริ่ม (Pre-conditions) | |
| เงื่อนไขหลังจบ (Post-conditions) | |
| ลำดับเหตุการณ์หลัก (Main Flow) | ไล่เป็นข้อ 1, 2, 3 สลับ "ผู้ใช้ทำ / ระบบตอบ" |
| ทางเลือก (Alternate Flows) | |
| ข้อยกเว้น (Exception Flows) | ทุกกรณีที่ระบบต้องปฏิเสธ |
| กฎทางธุรกิจ | อ้างคำศัพท์จาก `CONTEXT.md` |
| รหัสความต้องการที่ครอบคลุม | |

**ค. Activity Diagram** — ทำเฉพาะ UC ที่มีการตัดสินใจหลายทาง (มี Exception Flow ตั้งแต่สองกรณีขึ้นไป) ต้องมี decision node ครบทุกกรณีที่ระบุใน Exception Flows

**ง. DFD Level 1–2** — Level 1 แตกระบบเป็น process หลักของแต่ละโมดูล (1.0, 2.0, …) พร้อม data store; Level 2 แตกเฉพาะ process ที่มีตรรกะซับซ้อน (เช่น การตรวจสอบก่อนบันทึก) เลขลูกต้องสืบจากเลขแม่ (1.0 → 1.1, 1.2)

**จ. State Diagram** — ทำให้ทุก entity ที่มีสถานะ ต้องระบุ:
- สถานะเริ่มต้นและสถานะจบทุกทาง
- เหตุการณ์ (event) บนทุกเส้น ไม่ปล่อยเส้นเปล่า
- ใครมีสิทธิ์ทำให้เกิด transition นั้น

## บทที่ 4 — ความต้องการที่ไม่ใช่เชิงหน้าที่ (`04-non-functional-requirements.md`)

หนึ่งหัวข้อย่อยต่อหนึ่งหมวด ใช้ตารางเดียวกันทุกหมวด

| รหัส | ข้อกำหนด | ตัววัด (Metric) | เกณฑ์ยอมรับ | วิธีทดสอบ | ที่มา |
|---|---|---|---|---|---|

หมวดที่ต้องมีครบ:

- **4.1 Performance** (`NFR-PERF-*`) — เวลาตอบสนองต่อหน้าจอ/API, จำนวนผู้ใช้พร้อมกัน, ปริมาณธุรกรรมต่อวัน
  → **Workload / Concurrent User Chart** แสดงผู้ใช้พร้อมกันรายชั่วโมงในวันทำการ ชี้ชั่วโมงเร่งด่วน (peak)
- **4.2 Security** (`NFR-SEC-*`) — การเข้าถึง, การตรวจสอบสิทธิ์, การบันทึกร่องรอย (audit log), การเข้ารหัสข้อมูล
  ถ้า ADR ระบุว่าไม่มี authentication ต้องเขียนความเสี่ยงที่ตามมาไว้ตรง ๆ พร้อมอ้าง ADR และระบุเงื่อนไขที่ต้องเพิ่มก่อนใช้งานจริง
- **4.3 Availability** (`NFR-AVL-*`) — เวลาให้บริการ, ระดับ uptime, RTO/RPO, การสำรองข้อมูล
- **4.4 Usability** (`NFR-USE-*`) — จำนวนคลิกถึงเป้าหมาย, ภาษาที่รองรับ, การใช้งานบนมือถือ, ข้อความแจ้งข้อผิดพลาด
- **4.5 Compliance / PDPA** (`NFR-PDPA-*`) — ต้องสอดคล้องกับข้อมูลส่วนบุคคลที่ระบุไว้ในบทที่ 5 ครอบคลุมอย่างน้อย: ฐานการประมวลผล, การแจ้งวัตถุประสงค์, สิทธิเจ้าของข้อมูล (เข้าถึง/แก้ไข/ลบ), ระยะเวลาเก็บรักษา, การลบเมื่อครบกำหนด
- **4.6 Maintainability / Portability** (`NFR-MNT-*`) — ตามข้อจำกัดการติดตั้งใน ADR

## บทที่ 5 — ความต้องการด้านข้อมูล (`05-data-requirements.md`)

**5.1 ข้อมูลหลัก** — อธิบาย entity หลักและความสัมพันธ์เป็นร้อยแก้วสั้น ๆ ชื่อ entity ต้องตรงกับคำใน `CONTEXT.md`
→ **Conceptual ERD**

**5.2 Data Dictionary**

| Entity | Attribute | ชื่อภาษาไทย | ชนิดข้อมูล | บังคับ | คีย์ | กฎการตรวจสอบ | ข้อมูลส่วนบุคคล |
|---|---|---|---|---|---|---|---|

คอลัมน์ "ข้อมูลส่วนบุคคล" (ใช่/ไม่ใช่) เป็นตัวป้อนให้หัวข้อ PDPA ในบทที่ 4 — ต้องกรอกทุกแถว

**5.3 ปริมาณข้อมูลและการเติบโต**

| Entity | ปริมาณเริ่มต้น | อัตราเพิ่มต่อเดือน | ประมาณการ 3 ปี |
|---|---|---|---|

**5.4 การเก็บรักษาและการทำลายข้อมูล**

| ประเภทข้อมูล | ระยะเวลาเก็บ | การจัดการเมื่อครบกำหนด | ผู้รับผิดชอบ |
|---|---|---|---|

**5.5 การสำรองและกู้คืน** — ความถี่, ที่เก็บ, วิธีทดสอบการกู้คืน

## บทที่ 6 — ความต้องการด้าน Interface (`06-interface-requirements.md`)

**6.1 ส่วนติดต่อผู้ใช้ (User Interface)**

| รหัสหน้าจอ | ชื่อหน้าจอ | ผู้ใช้ | หน้าที่ | Use Case ที่รองรับ |
|---|---|---|---|---|

→ **Wireframe ระดับหยาบ** ของหน้าจอหลัก (อย่างน้อยหน้าจอที่รองรับ UC สำคัญ) ระดับกล่องและตำแหน่งเท่านั้น ไม่ลงสีหรือฟอนต์

**6.2 ส่วนติดต่อกับระบบภายนอก**
→ **Integration / Interface Diagram** แสดงทุก service, ทิศทางการเรียก, โปรโตคอล และรูปแบบข้อมูลบนเส้น

**6.3 รายการ API**

| รหัส | Method | Endpoint | คำอธิบาย | ผู้เรียก | รูปแบบข้อมูล | การยืนยันตัวตน | รหัสความต้องการ |
|---|---|---|---|---|---|---|---|

**6.4 ส่วนติดต่อกับฮาร์ดแวร์และสภาพแวดล้อม** — อุปกรณ์ที่รองรับ, เบราว์เซอร์และเวอร์ชันขั้นต่ำ, ความละเอียดหน้าจอ, ข้อกำหนดเครือข่าย ถ้าไม่มีข้อกำหนดด้านฮาร์ดแวร์ให้เขียนว่าไม่มีและบอกเหตุผล

## บทที่ 7 — ตารางสอบทานความต้องการ (`07-traceability-matrix.md`)

**7.1 ตาราง RTM**

| ข้อ TOR | ข้อความ TOR (ย่อ) | รหัสความต้องการ | ฟังก์ชัน / โมดูล | หัวข้ออ้างอิง | Use Case | สถานะ |
|---|---|---|---|---|---|---|

- หนึ่งข้อ TOR อาจกระจายไปหลายรหัส — แตกเป็นหลายแถว อย่ายัดหลายรหัสในช่องเดียว
- คอลัมน์ "หัวข้ออ้างอิง" ชี้ไปที่ไฟล์และหัวข้อจริง เช่น `03-functional-requirements.md §3.2`

**7.2 สรุปความครอบคลุม**

| ชนิดรหัส | จำนวนที่นิยาม | จำนวนที่อยู่ใน RTM | ข้อ TOR ที่ยังไม่มีรหัสรองรับ |
|---|---|---|---|

สองคอลัมน์กลางต้องเท่ากันทุกแถว ถ้าไม่เท่าให้กลับไปแก้บทต้นทาง ไม่ใช่แก้ตัวเลข

**7.3 รหัสที่ไม่มีต้นทาง TOR** — รหัสที่ทีมเพิ่มเองโดยไม่มีข้อ TOR รองรับ พร้อมเหตุผลว่าทำไมจำเป็น

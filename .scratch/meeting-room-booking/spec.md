# Meeting Room Booking — MVP

## Problem Statement

พนักงานในองค์กรจองห้องประชุมผ่านเจ้าหน้าที่ธุรการด้วยสมุดกระดาษ ต้องติดต่อทางโทรศัพท์หรือเดินไปพบในเวลาทำการของเจ้าหน้าที่เท่านั้น การตรวจว่าช่วงเวลาว่างหรือไม่ และห้องจุคนได้พอหรือไม่ อาศัยการอ่านสมุดและความจำของคน จึงเกิดการจองซ้อนทับกัน (Conflict) ได้บ่อย สมุดกระดาษเล่มเดียวทำให้ดูสถานะห้องพร้อมกันหลายคนไม่ได้ และทุกครั้งที่ถูกปฏิเสธ พนักงานต้องวนกลับไปคุยกับเจ้าหน้าที่ธุรการใหม่ทั้งหมด

## Solution

ระบบเว็บแอปพลิเคชันภายในองค์กรที่ให้พนักงานค้นหา Room ที่ว่างเอง เลือกช่วงเวลา และยืนยันการจองได้ทันทีโดยไม่ต้องผ่านเจ้าหน้าที่ธุรการและไม่ต้อง login กฎการจองสามข้อ — Business Hours, Capacity และ Conflict — ถูกบังคับที่ระบบเสมอทุกครั้ง ไม่มีการพึ่งพาสายตาคนอีกต่อไป เจ้าหน้าที่ธุรการเปลี่ยนบทบาทเป็นผู้ดูแลข้อมูล Room และ Employee เท่านั้น

ระบบตัวตนของ Employee ระบุจากการเลือกชื่อในรายการที่เตรียมไว้ล่วงหน้า ไม่มีรหัสผ่านหรือ session ที่ผ่านการยืนยัน (ที่มา: ADR-0002) — สิทธิ์แก้ไข/ยกเลิก Booking (Ownership) จึงอิงจากชื่อที่ผู้ใช้เลือกเอง ความเสี่ยงนี้เป็นที่ยอมรับสำหรับเฟสนี้ตามที่ผู้ว่าจ้างยืนยันไว้ (ดูหัวข้อ "Further Notes")

## User Stories

**ค้นหาและดูภาพรวม**

1. As a พนักงาน, I want to ค้นหา Room ที่ว่างโดยระบุวันที่ ช่วงเวลา และจำนวนผู้เข้าร่วม, so that ฉันเห็นเฉพาะห้องที่จองได้จริงโดยไม่ต้องเดา
2. As a พนักงาน, I want to กรองผลการค้นหาด้วยจำนวนผู้เข้าร่วม, so that ฉันไม่เห็นห้องที่จุคนไม่พอ
3. As a พนักงาน, I want to กรองผลการค้นหาตามอาคารหรือชั้น, so that ฉันหาห้องใกล้ที่ทำงานของฉันได้เร็วขึ้น
4. As a พนักงาน, I want to เห็นข้อความแนะนำเมื่อไม่พบห้องว่างตรงเงื่อนไข, so that ฉันรู้ว่าควรปรับช่วงเวลาหรือจำนวนผู้เข้าร่วมแทนที่จะค้นหาซ้ำแบบเดิม
5. As a พนักงาน, I want to เห็นข้อความแจ้งช่วงเวลาทำการที่อนุญาต เมื่อระบุช่วงเวลานอก Business Hours, so that ฉันแก้ไขช่วงเวลาได้ถูกต้องตั้งแต่ครั้งแรก
6. As a พนักงานหรือผู้ดูแลข้อมูล, I want to ดูปฏิทินการใช้งาน Room ทุกห้องของวันที่เลือก จัดกลุ่มตามห้องและเรียงตามเวลา, so that ฉันวางแผนเวลาประชุมหรือประเมินการใช้ห้องได้
7. As a พนักงานหรือผู้ดูแลข้อมูล, I want to กรองปฏิทินตามอาคารหรือชั้น, so that ฉันดูเฉพาะห้องที่เกี่ยวข้องกับฉัน

**สร้าง Booking**

8. As a พนักงาน, I want to เลือก Room จากผลการค้นหาแล้วไปหน้ายืนยันการจองทันที, so that ฉันจองได้ในเส้นทางสั้นที่สุด
9. As a พนักงาน, I want to พิมพ์ค้นหาและเลือกชื่อตนเองจากรายการ Employee เมื่อสร้าง Booking, so that ฉันระบุตัวเองเป็นเจ้าของได้เร็วแม้รายชื่อจะมีหลายร้อยคน
10. As a พนักงาน, I want to ระบบปฏิเสธการสร้าง Booking ที่ไม่ได้เลือกชื่อผู้จอง, so that ทุก Booking มีเจ้าของเสมอ
11. As a พนักงาน, I want to กรอกหัวข้อการประชุมและจำนวนผู้เข้าร่วมตอนยืนยันการจอง, so that คนอื่นที่เห็นปฏิทินรู้ว่าห้องถูกใช้ทำอะไร
12. As a พนักงาน, I want to ระบบปฏิเสธ Booking ที่ไม่ได้กรอกหัวข้อการประชุม, so that ปฏิทินไม่มีรายการที่ไม่มีความหมาย
13. As a พนักงาน, I want to ระบบปฏิเสธ Booking ที่เวลาเริ่มหรือเวลาสิ้นสุดอยู่นอก Business Hours, so that การจองทั้งหมดอยู่ในเวลาที่องค์กรอนุญาตให้ใช้ห้อง
14. As a พนักงาน, I want to ระบบปฏิเสธ Booking ที่จำนวนผู้เข้าร่วมเกิน Capacity ของ Room, so that ห้องที่จองไม่แน่นเกินความจุจริง
15. As a พนักงาน, I want to ระบบปฏิเสธ Booking ที่ช่วงเวลาซ้อนทับกับ Booking อื่นของ Room เดียวกัน, so that ไม่มีวันที่สองทีมมาเจอกันหน้าห้องเดียวกันโดยไม่รู้ตัว
16. As a พนักงาน, I want to ระบบปฏิเสธ Booking ที่เวลาสิ้นสุดไม่มากกว่าเวลาเริ่ม, so that ทุก Booking มีช่วงเวลาที่สมเหตุสมผล
17. As a พนักงาน, I want to ระบบปฏิเสธ Booking ที่เวลาเริ่มอยู่ในอดีต, so that ไม่มีใครจองย้อนหลังเพื่อปกปิดการใช้ห้องที่เกิดขึ้นแล้ว
18. As a พนักงาน, I want to เห็นเหตุผลการปฏิเสธเป็นภาษาไทยแยกเป็นรายข้อ เมื่อ Booking ไม่ผ่านกฎข้อใดข้อหนึ่งหรือหลายข้อพร้อมกัน, so that ฉันแก้ไขได้ถูกจุดโดยไม่ต้องลองผิดลองถูก
19. As a พนักงาน, I want to เห็นรายละเอียด Booking ที่บันทึกสำเร็จทันทีหลังยืนยัน, so that ฉันมั่นใจว่าจองสำเร็จแล้วจริง

**ดู แก้ไข และยกเลิก Booking ของตน**

20. As a พนักงาน, I want to เลือกชื่อตนเองแล้วดูรายการ Booking ทั้งหมดที่ฉันเป็นเจ้าของ เรียงจากใหม่ไปเก่า, so that ฉันตรวจสอบว่าจองอะไรไว้บ้าง
21. As a พนักงาน, I want to กรองรายการ Booking ของฉันให้เห็นเฉพาะรายการที่ยังไม่ผ่าน, so that ฉันโฟกัสเฉพาะสิ่งที่ยังต้องจัดการ
22. As a พนักงาน, I want to ดูรายละเอียดครบทุกฟิลด์ของ Booking หนึ่งรายการ, so that ฉันตรวจสอบข้อมูลก่อนเข้าประชุมได้
23. As a พนักงานเจ้าของ Booking, I want to แก้ไขช่วงเวลา ห้อง หัวข้อ หรือจำนวนผู้เข้าร่วมของ Booking ที่ยังไม่ผ่าน, so that ฉันปรับแผนประชุมได้โดยไม่ต้องยกเลิกแล้วจองใหม่
24. As a พนักงานที่ไม่ใช่เจ้าของ Booking, I want to ระบบปฏิเสธไม่ให้ฉันแก้ไข Booking ของคนอื่น, so that Booking ของคนอื่นไม่ถูกเปลี่ยนแปลงโดยฉันไม่ได้รับอนุญาต
25. As a พนักงาน, I want to ระบบปฏิเสธการแก้ไข Booking ที่เวลาสิ้นสุดผ่านไปแล้ว, so that ประวัติการใช้ห้องที่เกิดขึ้นแล้วไม่ถูกเปลี่ยนย้อนหลัง
26. As a พนักงาน, I want to ระบบตรวจกฎ Business Hours, Capacity และ Conflict ใหม่ทุกครั้งที่แก้ไข โดยไม่นับ Booking เดิมของฉันเป็น Conflict กับตัวเอง, so that การแก้ไขปลอดภัยเท่ากับการสร้างใหม่ แต่ไม่ถูกบล็อกด้วยรายการเดิมของตัวเอง
27. As a พนักงาน, I want to ระบบคงข้อมูลเดิมไว้ครบถ้วนเมื่อการแก้ไขไม่ผ่านกฎ, so that ฉันไม่เสีย Booking เดิมไปเพราะพยายามแก้ไขไม่สำเร็จ
28. As a พนักงานเจ้าของ Booking, I want to ยกเลิก Booking ที่ยังไม่ผ่าน พร้อมขอให้ยืนยันซ้ำก่อนยกเลิกจริง, so that ฉันไม่กดยกเลิกผิดโดยไม่ตั้งใจ
29. As a พนักงานที่ไม่ใช่เจ้าของ Booking, I want to ระบบปฏิเสธไม่ให้ฉันยกเลิก Booking ของคนอื่น, so that ไม่มีใครทำลาย Booking ของคนอื่นได้
30. As a พนักงาน, I want to ระบบปฏิเสธการยกเลิก Booking ที่เวลาสิ้นสุดผ่านไปแล้ว, so that ประวัติการใช้ห้องไม่ถูกแก้ไขย้อนหลัง
31. As a พนักงาน, I want to Room ที่ Booking ถูกยกเลิกกลับมาว่างทันทีในการค้นหาครั้งถัดไป, so that คนอื่นจองช่วงเวลานั้นแทนได้โดยไม่ต้องรอ

**จัดการข้อมูล Room (ผู้ดูแลข้อมูล)**

32. As a ผู้ดูแลข้อมูล, I want to ดูรายการ Room ทั้งหมดพร้อม Capacity อาคาร และชั้น, so that ฉันเห็นภาพรวมห้องประชุมทั้งหมดในองค์กร
33. As a ผู้ดูแลข้อมูล, I want to เพิ่ม Room ใหม่โดยระบุชื่อห้อง Capacity อาคาร และชั้น, so that ห้องที่เปิดใช้จริงปรากฏในระบบให้จองได้
34. As a ผู้ดูแลข้อมูล, I want to แก้ไขข้อมูล Room ที่มีอยู่, so that ข้อมูลห้องในระบบตรงกับความเป็นจริงเสมอ
35. As a ผู้ดูแลข้อมูล, I want to ปิดการใช้งาน Room ชั่วคราวเมื่อห้องปิดปรับปรุง โดย Room นั้นต้องไม่ปรากฏในผลการค้นหาห้องว่างอีก, so that พนักงานไม่จองห้องที่ใช้งานจริงไม่ได้
36. As a ผู้ดูแลข้อมูล, I want to ระบบปฏิเสธการลบ Room ที่มี Booking ที่ยังไม่ผ่านค้างอยู่ พร้อมแจ้งจำนวนรายการที่ค้าง, so that ฉันไม่ลบห้องที่มีคนจองไว้แล้วโดยไม่รู้ตัว
37. As a ผู้ดูแลข้อมูล, I want to ระบบปฏิเสธการลด Capacity ของ Room ให้น้อยกว่าจำนวนผู้เข้าร่วมสูงสุดของ Booking ที่ยังไม่ผ่านของห้องนั้น, so that ฉันไม่ทำให้ Booking ที่มีอยู่แล้วผิดกฎย้อนหลัง

**จัดการรายการ Employee (ผู้ดูแลข้อมูล)**

38. As a ผู้ดูแลข้อมูล, I want to ดูรายการ Employee ทั้งหมดพร้อมหน่วยงานและสถานะ, so that ฉันตรวจสอบว่ารายชื่อในระบบตรงกับบุคลากรปัจจุบัน
39. As a ผู้ดูแลข้อมูล, I want to เพิ่มและแก้ไขชื่อ นามสกุล และหน่วยงานของ Employee, so that พนักงานเลือกชื่อตนเองได้ถูกต้องตอนสร้าง Booking
40. As a ผู้ดูแลข้อมูล, I want to เห็นคำเตือนเมื่อชื่อและนามสกุลที่กรอกซ้ำกับรายการที่มีอยู่, so that ฉันไม่สร้างรายชื่อซ้ำที่ทำให้พนักงานเลือกผิดคน
41. As a ผู้ดูแลข้อมูล, I want to ปิดการใช้งาน Employee ที่พ้นสภาพ โดยไม่ลบ Booking เดิมของ Employee นั้น, so that ประวัติการใช้ห้องยังคงอยู่ครบถ้วนแม้คนนั้นออกจากองค์กรไปแล้ว

**ตั้งค่า Business Hours (ผู้ดูแลข้อมูล)**

42. As a ผู้ดูแลข้อมูล, I want to ดูและแก้ไขค่าตั้งค่า Business Hours รายวันในสัปดาห์ โดยไม่ต้องแก้โปรแกรม, so that องค์กรปรับเวลาทำการได้เองเมื่อจำเป็น

**ความปลอดภัยและร่องรอยการใช้งาน**

43. As a ฝ่ายเทคโนโลยีสารสนเทศ, I want to ระบบบันทึกร่องรอยการสร้าง แก้ไข และยกเลิก Booking ทุกครั้งพร้อมเวลาและชื่อ Employee ที่ผู้ใช้ระบุ, so that ตรวจสอบย้อนหลังได้เมื่อเกิดข้อโต้แย้งเรื่องการจอง
44. As a ฝ่ายเทคโนโลยีสารสนเทศ, I want to ระบบจำกัดจำนวนคำขอสร้าง Booking จาก IP เดียวกันไม่เกิน 30 ครั้งต่อนาที, so that ระบบไม่ถูกใช้งานผิดปกติจนกฎ Conflict ทำงานผิดพลาดหรือฐานข้อมูลรับภาระเกิน
45. As a เจ้าหน้าที่คุ้มครองข้อมูลส่วนบุคคล, I want to ระบบลบหรือทำให้ข้อมูลส่วนบุคคลของ Booking ที่เก่าเกิน 2 ปีไม่ระบุตัวตน คงไว้เฉพาะห้อง ช่วงเวลา และจำนวนผู้เข้าร่วมสำหรับทำสถิติ, so that องค์กรไม่เก็บข้อมูลส่วนบุคคลนานเกินความจำเป็นตาม PDPA

## Implementation Decisions

**สถาปัตยกรรมและขอบเขต (อ้างอิง ADR-0001 ถึง ADR-0004)**

- ระบบเป็น single-tenant องค์กรเดียว ไม่มีแนวคิด Organization/Tenant ในโมเดลข้อมูล (ADR-0001)
- ไม่มีระบบ authentication ใดๆ ตัวตนของ Employee ระบุจากการเลือกชื่อในคำขอ (request body/query) ไม่ใช่จาก session หรือ token — ทุก endpoint จึงไม่มีการยืนยันตัวตน (ADR-0002)
- ฐานข้อมูลเป็น SQLite ไฟล์เดียว เข้าถึงผ่าน Prisma ORM (ADR-0003)
- แยกเป็นสอง service ภายใน monorepo เดียวกัน: **Backend** (Express + TypeScript) ถือ Prisma/SQLite และ business logic ทั้งหมด (Business Hours, Capacity, Conflict, Ownership) และ **Frontend** (Next.js + TypeScript + Tailwind + shadcn/ui) เป็น UI ล้วน เรียก Backend ผ่าน REST/JSON เท่านั้น ไม่มี Prisma หรือ API routes ของตัวเอง (ADR-0004)
- Backend เปิด CORS เฉพาะ origin ของ Frontend ที่กำหนดในค่าตั้งค่า
- หน้าจอผู้ดูแลข้อมูล (จัดการ Room, จัดการ Employee) อยู่คนละเส้นทาง URL กับหน้าจอพนักงาน เพื่อให้จำกัดการเข้าถึงที่ระดับเครือข่ายได้ในอนาคต โดยไม่มีการตรวจสิทธิ์ในโค้ดฝั่งเซิร์ฟเวอร์ในเฟสนี้

**โมดูล**

- **RoomModule** (Backend) — CRUD ของ Room, บังคับกฎ "ห้ามลบ Room ที่มี Booking ค้าง" และ "ห้ามลด Capacity ต่ำกว่าที่จองไว้แล้ว" ก่อนเขียนลงฐานข้อมูล
- **EmployeeModule** (Backend) — CRUD ของ Employee, ค้นหาด้วยบางส่วนของชื่อ/นามสกุล, ตรวจชื่อซ้ำแบบ warn-not-block (แจ้งเตือนแต่ยังบันทึกได้ถ้าผู้ใช้ยืนยันซ้ำ)
- **BookingModule** (Backend) — จุดเดียวที่บังคับกฎทั้งสี่ข้อ (ความครบถ้วนของข้อมูล → ความถูกต้องของช่วงเวลา → Business Hours → Capacity → Conflict → Ownership เมื่อแก้ไข/ยกเลิก) เรียงลำดับจากตรวจเร็วที่สุดไปช้าที่สุด (อ่านฐานข้อมูลน้อยไปมาก) ใช้ร่วมกันทั้งเส้นทางสร้างและแก้ไข โดยการแก้ไขต้องไม่นับ Booking แถวที่กำลังแก้ไขเป็น Conflict ของตัวเอง
- **BusinessHoursModule** (Backend) — อ่าน/เขียนค่าตั้งค่ารายวันในสัปดาห์ เป็นค่ากลางระดับระบบ (ไม่แยกตามห้อง) ตามที่ผู้ว่าจ้างยืนยัน
- **BookingAuditModule** (Backend) — บันทึกร่องรอยทุกครั้งที่ BookingModule สร้าง แก้ไข หรือยกเลิก Booking สำเร็จ ทำงานภายในธุรกรรมเดียวกับการเขียน Booking

**กฎการบังคับ Conflict**

- กฎ "ห้าม Booking สองรายการของ Room เดียวกันที่สถานะยืนยันแล้วมีช่วงเวลาซ้อนทับกัน" ต้องบังคับที่ระดับฐานข้อมูลหรือภายในธุรกรรมเดียวกันกับการเขียน ไม่ใช่แค่ตรวจที่ชั้นแอปพลิเคชันก่อนเขียนแยกขั้นตอน เพื่อป้องกัน race condition เมื่อมีคำขอสร้าง Booking สำหรับ Room เดียวกันพร้อมกัน

**สถานะของ Booking และ Room**

- Booking มีสามสถานะ: ยืนยันแล้ว, ยกเลิกแล้ว, เสร็จสิ้น — มีเพียงสถานะยืนยันแล้วเท่านั้นที่ถูกนับเป็น Conflict การยกเลิกเปลี่ยนสถานะ ไม่ลบแถว การเปลี่ยนเป็นเสร็จสิ้นเกิดขึ้นเองเมื่อเวลาสิ้นสุดผ่านไป (ไม่ต้องมี background job แยก — คำนวณจาก `end_at` เทียบเวลาปัจจุบันตอน query ก็เพียงพอสำหรับเฟสนี้)
- Room มีสองสถานะ: เปิดใช้งาน, ปิดการใช้งานชั่วคราว — Room ที่ปิดใช้งานไม่ปรากฏในผลการค้นหาห้องว่าง แต่ Booking เดิมที่ผูกอยู่ยังคงอยู่ไม่ถูกยกเลิกอัตโนมัติ

**ข้อมูล (สรุปจาก docs/sds/05-data-requirements.md ซึ่งเป็นแหล่งอ้างอิงฉบับเต็ม)**

- ห้าหน่วยข้อมูล: ROOM, EMPLOYEE, BOOKING, BOOKING_AUDIT, BUSINESS_HOURS ความสัมพันธ์ทั้งหมดเป็นหนึ่งต่อกลุ่ม BOOKING เป็นหน่วยกลางเชื่อม ROOM กับ EMPLOYEE
- Booking หนึ่งแถวต้องอ้างถึง Room หนึ่งแถวและ Employee หนึ่งแถวเสมอ ปฏิเสธการบันทึกที่ขาดอย่างใดอย่างหนึ่ง
- เวลาทั้งหมดเก็บและตีความในเขตเวลา Asia/Bangkok เขตเดียว
- การลบ Employee (เมื่อได้รับคำขอลบข้อมูลตาม PDPA) ต้องลบค่า `employee_id` และ `title` ของ Booking ทุกรายการของบุคคลนั้นก่อน แล้วจึงลบแถว EMPLOYEE

**API Contract (สรุปจาก docs/sds/06-interface-requirements.md หัวข้อ 6.3 ซึ่งเป็นแหล่งอ้างอิงฉบับเต็ม)**

- REST/JSON ผ่าน HTTPS ไม่มีการยืนยันตัวตนในทุก endpoint (`/api/rooms`, `/api/rooms/available`, `/api/employees`, `/api/bookings`, `/api/bookings/{id}/cancel`, `/api/business-hours` และ CRUD ที่เกี่ยวข้อง)
- การยกเลิก Booking ใช้ `POST /api/bookings/{id}/cancel` แทน DELETE เพราะเป็นการเปลี่ยนสถานะ ไม่ใช่การลบข้อมูล
- รหัสสถานะที่ต้องตอบกลับอย่างสม่ำเสมอ: `400` เมื่อข้อมูลไม่ครบ/ผิดรูปแบบ พร้อมรายการฟิลด์ที่ไม่ผ่าน · `409` เมื่อไม่ผ่านกฎ Business Hours/Capacity/Conflict พร้อมรหัสเหตุผลที่จับคู่หนึ่งต่อหนึ่งกับข้อความภาษาไทยบนหน้าจอ · `403` เมื่อ Employee ที่ระบุไม่ใช่เจ้าของ Booking · `429` เมื่อเกิน rate limit ของการสร้าง Booking

## Testing Decisions

- **ชีมทดสอบเดียว**: ทดสอบผ่าน HTTP endpoint ของ Backend Express app จริง (เช่นด้วย supertest) กับฐานข้อมูล SQLite จริง (ไฟล์ทดสอบแยกต่างหาก หรือรีเซ็ตข้อมูลก่อนแต่ละเทสต์ผ่าน Prisma) ไม่ mock Prisma/DB layer เพราะกฎ Conflict ต้องพิสูจน์ผ่านการเขียนจริงจึงจะน่าเชื่อถือ — นี่คือชีมเดียวที่ครอบคลุมทั้ง RoomModule, EmployeeModule, BookingModule และ BusinessHoursModule
- ทดสอบเฉพาะพฤติกรรมภายนอกที่สังเกตได้ผ่าน request/response (status code, response body, ผลกระทบที่อ่านคืนได้จาก GET ถัดไป) ไม่ทดสอบรายละเอียดภายใน เช่น query ที่ Prisma สร้าง หรือโครงสร้างไฟล์ภายใน route handler
- ลำดับความสำคัญของเทสต์: กฎการบังคับใน BookingModule (Business Hours, Capacity, Conflict, Ownership, ช่วงเวลาไม่ถูกต้อง, จองย้อนหลัง) เป็นกลุ่มที่ต้องมี coverage สูงสุดเพราะเป็นแก่นของปัญหาที่ระบบนี้แก้ (การจองซ้อนทับที่เกิดจากกระบวนการเดิม) — โดยเฉพาะเทสต์ concurrent request สองคำขอสร้าง Booking ของ Room เดียวกันพร้อมกัน ต้องมีเพียงคำขอเดียวสำเร็จ
- ไม่มี prior art ในโค้ดเดิม เพราะเป็นโปรเจกต์ที่ยังไม่มีโค้ดใดๆ (greenfield) — ชุดเทสต์แรกของ BookingModule จะเป็นแบบแผนอ้างอิงสำหรับโมดูลถัดไป
- Frontend ทดสอบแยกในระดับ component/interaction เท่านั้น (ไม่ทดสอบ business logic เพราะไม่มีอยู่ที่ frontend) อยู่นอกชีมหลักของสเปกนี้

## Out of Scope

- ระบบ authentication/login ใดๆ (ADR-0002) — รวมถึงหน้า login สำหรับผู้ดูแลข้อมูล ผู้ว่าจ้างยืนยันว่ามีแผนเพิ่มในอนาคตแต่ไม่ใช่เฟสนี้
- Booking แบบเกิดซ้ำตามรอบ (recurring) — Booking เป็นการจองครั้งเดียวเสมอ (CON-08)
- Booking ที่ผูกกับหลาย Room หรือหลาย Employee เจ้าของ (CON-09)
- การเชื่อมต่อระบบข้อมูลบุคลากร (HR) เพื่อนำเข้ารายชื่อ Employee อัตโนมัติ — เตรียมโครงสร้างข้อมูลให้รองรับในอนาคตเท่านั้น (`IR-09`) ไม่ใช่การเชื่อมต่อจริง
- การแจ้งเตือนผ่านอีเมลหรือปฏิทินภายนอก (ASM-12, ยืนยันแล้วว่าไม่ต้องการ)
- การรองรับหลายองค์กร (multi-tenant) และการขยายแนวราบ (multi-instance deployment) (ADR-0001, ADR-0003)
- Business Hours แยกตามรายห้อง — ยืนยันแล้วว่าเป็นค่ากลางระดับระบบเดียวสำหรับทุกห้อง
- การยืนยันการเข้าใช้ห้องจริง (เช่น เครื่องอ่านบัตร หรือเซนเซอร์) — อยู่นอกขอบเขตตามหัวข้อ 1.2.2 ของ SRS
- การจับคู่รหัสกับเอกสาร TOR ฉบับทางการ — ยังไม่มีเอกสาร TOR จริง (ASM-01) ขอบเขตนี้อิงจากการยืนยันตรงจากผู้ว่าจ้างเท่านั้น

- ยังไม่มีเอกสาร TOR ฉบับทางการ (ASM-01) — เมื่อได้รับในอนาคต ต้องนำ RTM ในบทที่ 7 ของ SRS มาจับคู่รหัสใหม่ทั้งตาราง
- สเปกนี้ครอบคลุมทั้ง 30 ข้อกำหนดเชิงหน้าที่ (FR) ใน 3 โมดูล (ROOM, EMP, BKG) ตามบทที่ 3 ของ SRS — เมื่อแตกเป็น ticket ด้วย `/to-tickets` ควรแตกตาม tracer bullet ที่เดินจบ end-to-end ได้ทีละเส้น เช่น "ค้นหา + สร้าง Booking พื้นฐาน" ก่อน แล้วค่อยเพิ่มกฎและ use case ที่เหลือ แทนที่จะแตกตามโมดูลเพียงอย่างเดียว
